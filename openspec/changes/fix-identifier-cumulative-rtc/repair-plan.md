# 数字增量跟读与原生 RTC 播放修复计划

状态：**原生播放取舍与 Final 重答规则已确认；本文已更新，供用户复阅；尚未实施本计划。** 日期：2026-10-28。

本文件描述拟调整的方案，不覆盖尚在生效的 design / Delta Spec。正式开发前先同步受影响规格、设计、决策和任务；本次仅更新方案及确认记录。已确认保留数字跟读及编号收集；用户已认可本次截取的真实录音作为样本。

## 一、需求理解

用户分段念编号时，系统应及时跟读新内容，正确累计，不能因为 ASR 重复返回整串而重复念旧数字。Partial 满足现有条件即可触发，不等待 Final、Jev 或对话 LLM。普通对话仍使用已确认的 Jev 话轮策略。

手机应正常连接、播放、挂断和重连。保留数字跟读，已确认恢复浏览器原生 RTP/Opus 音轨播放，移除逐包身份匹配作为通话成功的前置条件。300ms 是“停口到首个跟读音”的优化目标，尚不是经过验证的上线承诺。

## 二、本次已核实的问题

| 问题 | 证据与边界 |
|---|---|
| 新增数字误当整段更正 | PC 会话 935dbcf8 中，1234 后新增5，却安排整段12345；该任务后来取消 |
| 格式变化重复播 | 同会话的“1, 2, 3, 4, 5, 3.”变成“123453.”，再次安排并开播整段；排队约3.2秒 |
| 手机匹配失败挂断 | 最新98f5840b已连接、加载最新版本，随后mapping_deadline；Jev返回成功 |

已复现“已处理包重复到达可能误触发匹配超时”，但不把它当成最新手机故障的唯一已证实根因。原来缓存读取约2–16ms，没有临时合成，不能用降低TTS耗时解释这次秒级排队。

## 三、拟修复的产品行为

### 1. 增量跟读

先用既有词表把同一来源的转写归一为数字/字母单元，再区分内容关系；标点和格式不是新的内容。维护已发送与待发送的单元范围，不依赖“字符串是否完全相同”决定整段补读。

| 变化与状态 | 期望行为 |
|---|---|
| 123 → 123456；123已发送 | 仅追加456，收集结果123456 |
| 123 → 123456；仅1已发送，23待发 | 保留待发23，再接456；不重发1、不漏23 |
| 123 → 123456；123尚在排队 | 更新/合并待播任务，最终每个有效单元只发送一次 |
| 1, 2, 3 → 123 | 不新增播放任务，不重复累计 |
| 同一来源重复Partial/Final | 幂等处理，不重复播 |
| 123 → 124；旧任务未发送 | 替换待播旧任务 |
| 123 → 124；旧片段已发送 | 作为真正更正，按既有补读规则安排最新有效片段；连续未发送修订合并 |
| 1122 → 112233 | 保留重复数字，只追加33，不按数字值去重 |
| 新来源恰好也是123 | 按新输入范围收集，不能误当重复事件 |
| 清空后旧转写/旧音频准备完成 | 旧代次失效，不恢复旧编号或继续发送旧任务 |

“已发送”不等于用户已听见。原生播放下以服务端发送事实控制幂等和更正，无法精确确认已听范围时如实保留未知状态。真正更正仍可能需要重复纠正片段，这与普通追加只播尾部不同。

### 2. RTC 播放简化（用户已确认）

声音继续通过WebRTC RTP/Opus音轨，由浏览器原生播放器处理。保留服务端播放任务ID、串行仲裁、清空与过期任务取消；不再要求浏览器逐包匹配任务、WebCodecs解码或任务级开播/停止回执才能通话。数据通道继续承担必要控制消息，不传PCM音频。

- 普通回答、跟读、提醒进入同一服务端输出顺序，避免两套声音重复播放。
- 清空、普通回答被打断或符合下节条件的 Final 内容修订：停止旧任务的后续生成与发送，清掉对应未发送队列；按既有顺序启动新内容。
- 已发到浏览器缓冲的声音可能留下短暂尾音；不能承诺精确停止某个任务的最后一个样本。
- 历史中的客户端任务开播/停止及相关延迟字段标明不支持或未知，不以入队、发送或原生音轨活动伪造任务实际播放。
- 移除旧身份匹配/回执超时触发的挂断路径；保留真实ICE断连、鉴权、厂商失败等错误处理和名额释放。
- 改动以RTC下行为主；管理页Test bot入口及现有WebSocket链路分别回归，不假设两者是同一播放实现。

#### 服务端排队与发送

TTS生成完成、服务端发送完成、用户听完是三个不同状态。发送完成以音频按实时节奏经过服务端输出及transport队列为依据，不能把整段PCM交给内部队列等同于发送完成。

- 普通回答、跟读、提醒共用一个串行发送出口；上一任务最后一帧按发送节奏交付后，再接下一任务，不等待客户端开播、结束或停止回执。
- 根据音频长度、采样率及单调时钟控制发送节奏，并限制可提前排入transport的音频量；网络背压时不得无限堆积。具体缓冲上限须在design明确并经测试验证，不伪装成客户端播放进度。
- 取消时同时清理生成任务、业务待发队列及可清理的transport旧音频；检查任务版本，阻止迟到音频重新进入。已进入网络或浏览器缓冲的声音允许短暂残留。
- 跟读期间普通续说仍不打断有效跟读；清空旧编号、普通回答打断、Final重答等沿用各自取消范围，不把所有续说都处理为清空。
- 记录生成结束、发送开始/结束、取消、剩余服务端队列时长；客户端实际听到范围保持未知。原生播放卡顿、页面暂停等不能仅凭发送完成判断已听完。

### 3. Final 到达后的回答处理（用户已确认）

Jev判断是否说完，ASR Final确认识别文字，两者独立。保留当前有界Final等待：轮次允许结束但Final未到时，等待窗口到期可用Partial启动LLM；不要求所有回答必须等待Final。

| 情况 | 处理 |
|---|---|
| Final在提交LLM前到达 | 更新候选文字，按既有TD规则提交，不重答 |
| 已用Partial启动回答，首个有效Final文字完全相同 | 更新最终转写状态；原回答继续，不重新请求LLM/TTS |
| 同上，仅标点或空格变化 | 同样不重答，不取消原声音 |
| 同上，除标点、空格外的内容变化 | 停止对应旧回答生成及后续发送，清理其未发送声音，更新有效上下文，用Final重新回答 |
| 重复Final、已处理版本或已过期旧轮次Final | 不重复重答，不打断新轮次 |

判定是确定性的文字比较：比较副本仅移除Unicode标点及空白，原文保留用于展示与上下文；其余字符不同即视为内容变化，不再调用模型判断是否同义，不擅自忽略大小写、数字或否定词差异。标点和空格即使可能影响含义，本方案仍按用户确认不触发重答。

不重答时也须更新有效转写及后续上下文，不把Partial永久保留为最终记录。重答仍属于同一用户轮次，保留已发送事实；已执行工具副作用不得因重答再次执行。此规则替代原“Final相同也重答”的契约；不是恢复此前已修复的重复字幕，不改变ASR事件本身。

### 4. 延迟与识别核查

记录最后人声、有效Partial到达、规则满足、首次音频发送、可测的实际播放时间。ASR等待与静音等待可以重叠，不机械相加。先消除重复整串和过时队列，再评估阈值；线上现有200ms停顿不擅自改为300ms。

300ms目标优先观察缓存命中、无前序音频阻塞的跟读；追加时前段正在播放的情况单列。报告样本数及分布，小样本不宣称稳定P95。原生播放无法直接提供任务级回执，自动测试可用已知音频波形和测试端采集测量；若无法可靠测量，明确未验证，不用回执往返冒充实际听感延迟。

## 四、真实录音与自测标准

已获用户认可的样本：PC会话935dbcf8，原录音27–42秒，15秒，16kHz单声道。用户上行录音不包含机器人声音。

本地路径：`/tmp/voiceagent-private-regression-935dbcf8/digits-27s-42s.wav`；相邻`manifest.json`记录来源与校验值。完整下载副本已清理；此目录是临时私有工作目录，不是永久语料库。录音不提交Git、不放公开静态资源，后续保留/迁移须沿用私有路径。

两层测试分别验收，不能混为一谈：

1. **固定转写回放，无外部收费调用：**重放真实历史ASR事件及其顺序，复现旧代码重复播报；修复后检查收集值、每个任务实际输出的音频单元、取消和发送顺序。同时补充理想123456789、重复数字、部分发送、撤回、插入、真更正、格式变化、迟到Final等边界。另测Final相同/仅标点空格变化时LLM调用数不增加，内容变化时仅重启一次；旧轮次不打断新轮次、工具副作用不重复。
2. **真实音频回放：**先人工听辨并标注数字、停顿及不确定处，恢复“请提供11位号码”的上下文。真实ASR返回错误数字时，必须归为识别问题，不能要求跟读模块凭空纠正成用户期望号码。若调用真实ASR，另行取得针对片段、厂商、次数、费用上限及停止条件的授权。

该录音能验证语速/停顿和ASR链路，不能复现昨天的真实网络条件，也不能替代手机兼容性测试。

不承诺当前环境能自动覆盖真实Android/iOS扬声器、AEC、蓝牙和运营商网络。自动化先做完，必须人工核验的部分集中成一次短清单；无法验证的项不能标通过。

## 六、待确认与回退边界

已确认：**保留跟读/编号累计与服务端取消，恢复浏览器原生音轨；接受短暂缓冲尾音、系统不能精确知道听到哪里。Final相同或仅标点、空格变化不重答，内容确实变化才重答。** 不再重复请求用户确认这两项决定。

本次仅更新文档，供用户复阅，不据此修改生产。具体尾音时长尚未测得，也未获数值验收确认。研发须测量取消生效到最后一段旧声音结束的时间，在正常网络和扰动场景分别报告样本及结果；持续读出旧队列、多出整段旧编号或旧任务继续发送均视为缺陷。结果与用户接受的“一小截”明显不符时先修复，不能自行标记通过；需数值取舍时带实测结果再确认。

发布前保存代码版本和必要配置回退依据，不迁移/清空用户数据。旧版本已经存在故障，回退只能撤销新回归，不能声称旧版稳定。若新方案出现严重问题，停止继续发布并报告；未经用户同意不关闭数字跟读/编号收集。

## 附录：研发必须注意

- 比较单位是同一来源范围的规范化单元；不得用全局文本前缀或最长公共子串推断音频归属。
- 区分queued、已发送、发送中；先前任务失效时重新计算待发范围，不能产生重叠或漏掉未发尾段。
- 回调/ASR修订/清空需检查来源版本与collection generation，避免迟到任务复活。
- 当前Spec/design中的严格回执、能力不足失败、逐包身份约束及Final无条件重答契约会被本方案改变，必须同步修改，不能只改前端绕开校验。
- 检查RTC session协议声明、服务端transport、输出等待、旧worker、输入时钟/上行录音依赖以及历史统计；删除下行依赖不能损坏上行。
- 不新增生产依赖，不更换ASR厂商，不借本次修复调整Jev融合参数。需要额外架构/成本变化时另行说明。
