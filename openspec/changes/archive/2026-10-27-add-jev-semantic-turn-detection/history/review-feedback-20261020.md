# 自建 TD：SDD + TDD 自测范围（待确认）

日期：2026-10-20。状态：范围提案，尚未获用户确认；没有开始核心开发、真实厂商测试或产品验收。

## 先看这一页

目标不是让产品经理理解框架内部代码，而是证明：**不抢话、不漏收、不重复回复、编号正确、播放不串、延迟可解释。**

推荐流程：确认行为规格（SDD）→ 给每项行为写能发现错误的测试（TDD）→ 看到测试因目标行为缺失而失败 → 最小实现 → 测试通过 → 真实链路验证 → 独立验收。

你负责决定用户应听到什么、何时清空等产品行为。我负责事件适配、时钟、版本、错误处理和测试实现；不把“厂商有没有时间戳”等工程事实交给你猜。

| 层级 | 自测范围 | 怎样测 | 通过依据 |
|---|---|---|---|
| A：ASR 输入 | 四家六模型的 Partial、Final、范围、修订和时间戳 | 构造协议事件测试适配器；再用无敏感音频跑真实流式调用 | 文本不重复不丢失；源事件→框架→TD时间可追溯；逐模型报告Partial时间可用性 |
| B：轮次控制 | 候选停顿、续说、Jev、Final等待、最长截止和断流 | 可控制时间和事件先后，不用真实等待碰运气 | 一次用户轮次仅提交一次；旧结果不影响新候选；普通路径截止不被延长 |
| C：编号与播放 | 收集、跟读、修订、提醒、清空、新一轮采集和输出冲突 | 固定输入/事件/播放回执，按填写后的播放表断言 | 编号值及实际播放顺序与规格一致；过期任务不能回写或播放 |
| D：真实音频体验 | Silero、人机同时说话、回声、首播和完整性 | 先本地非敏感录音回放；再实机耳机/扬声器测试 | 有录音、事件和客户端开播证据；合成事件测试不冒充听感验收 |
| E：完整产品 | 配置、密钥、缓存发布、会话历史和已有模式回归 | 复用现有API/页面测试及正式路由；刷新/重启/失败注入 | 新配置隔离持久化；指标真实；provider_native/off与普通打断不退化 |

建议本轮范围：浏览器 WebSocket 与已有 WebRTC 路径；固定四家六模型；英文、阿拉伯语及两者混说为主要效果样本，中文覆盖已约定的编号/前缀/控制句。并非承诺六模型都支持全部语言：按各模型支持范围执行，英语模型不拿阿语测试判失败。不包含电话接入、新声学TD模型或新建服务。

## 12条反馈：用具体例子解释

### 1．Partial 提交后的转写怎么分

:codex-annotation{index="1"}

建议给每次已提交内容记一份“收据”：当时交了哪些字、来自哪段音频。后续ASR即使把旧话和新话一起发来，也按音频范围核对收据。

例如已提交“我要转账”，下一包是“我要转账给张三”：旧范围的“我要转账”不再交一次；新范围的“给张三”保留给后续轮次，继续沿用普通打断规则。**不能只按字符串删前缀**，因为用户可能真的重复说相同内容。

工程会测试范围清楚、范围跨界、缺少细粒度时间及ASR修订的情况。不能可靠拆分时记录范围不确定，不能假装已经正确切开。同范围有效Final将已提交文字改成另一意思时，按D-043停止对应旧回答并重答；保持原请求快照，更新有效对话上下文并记录修订。不能仅在后台改字而让旧请求继续，也不能打断已经进入的新轮次。

### 2．为什么用户已经说话，VAD还没确认

:codex-annotation{index="2"}

VAD需要听到一小段声音，才能区分“人开口了”还是“碰了下麦克风”。这段确认时间里，用户可能已经在说话。

| 时间（仅示意） | 发生什么 |
|---|---|
| 机器人原计划800ms开始处理回复 | 还在等用户是否继续 |
| 750ms | 用户已经开口；VAD发现疑似语音，但尚未确认 |
| 800ms | 原定等待到期：此时直接提交就可能抢话 |
| 950ms | VAD才正式确认用户在说话 |

建议800ms时先检查“有没有正在确认的新语音”：有就暂缓；确认是人声则取消旧候选，确认是噪声则恢复。测试会覆盖截止前一帧、同一帧和后一帧。这个机制只能保护已经收到/处理到的语音，不能保证知道网络另一端尚未传来的声音；延长等待的边界仍须写入Spec，不暗中突破最长截止。

### 3．播放清单

:codex-annotation{index="3"}

播放规则见 [playback-decisions.md](../decisions/playback-decisions.md)。用户已填写并确认，按实际用户选择写测试，不以推荐列替代。

### 4．one moment、123后提问，以及不是123是124

:codex-annotation{index="4"}

`one moment`这个例子撤回：它不是连续数字串，不能因词表里有one就直接收1。原有“单个有效编号单元可以成为候选”也不等于普通句子中的数字词都能收集；保留独立念号的正例与普通短语的反例，不擅自增加固定片段位数。

本轮严格分流已替代同句提取：同一候选“123，接下来还要几位”整体走Jev→LLM，不先本地收集或跟读；正常提供编号需工具提交。若123此前已作为独立纯编号实际处理，则后续问题不能造成重复收集。分别测试同句混合与先前已独立处理。

“不是123，是124”建议第一版沿用已定更正规则：作为一次更正请求，清空，提示重念完整编号；既不累计123124，也不擅自把124当成整份新编号。需要特别测试Partial先出现123、随后才出现否定/更正时能否撤销待播任务。若123已经实际播出，不能撤回用户已听到的音频。该更正清空行为已获用户明确确认，Q-038已闭环；不再用本地更正句式正则作为意图判断。

### 5．聚合器是什么意思

:codex-annotation{index="5"}

聚合器就是现有系统里“攒用户文字、决定何时递给LLM”的模块。现在它可以听ASR厂商的结束通知；新增自建TD后，应只听自建TD的最终提交通知。

我担心的是：你配置要再等，现有模块却仍按旧规则自动递交，等于两个人同时决定“用户说完了”。修复由工程负责，测试要故意发送厂商结束信号、框架超时信号，证明它们不能越过自建TD。原生模式仍保持原来的控制方式。

### 6．断流与静音有什么不同

:codex-annotation{index="6"}

两秒听不到声音有两种原因：用户安静了；或者网络断了，声音没传过来。前者可以正常判断话轮，后者并不知道用户是否还在说。

建议同时检查“音频还在持续到达吗”和“VAD已经处理到哪里”。音频正常且确认为静音，才走正常结束；断流走连接异常处理，不伪造用户已说完。测试会让音频停发、处理排队、重连后重置时间，检查不误交、不死等；具体恢复/结束行为沿用会话契约，冲突再提具体选择。

### 7．Jev返回数据为什么也要测

:codex-annotation{index="7"}

例如模型给三项概率0.333、0.333、0.333，加起来0.999：可能只是精度差，不能一律当坏数据。如果返回负概率、漏了一类或请求失败，则不能继续套公式。

还要防止“模型判断的是旧文字”：拿123问Jev，ASR随后改成124，旧结果就不能直接替124作决定。测试会覆盖数值、缺字段、超时、文字变化与迟到结果。容差、节流等由工程提出明确配置建议，不让你手算概率。

两种Jev问题是同一个模型从两个角度回答，不保证两个答案都准确；现有融合方向保留，最终效果用实际样本验，不把公式算对当作判断质量合格。

### 8．Jev听不到语气是什么意思

:codex-annotation{index="8"}

同一句“我想一下”，人可能在犹豫，也可能已经说完并等待回答。只把文字给Jev，它不知道真实语气。Silero只提供有没有人声的判断，也不解释语气。

不是建议现在加模型，而是用拖音、犹豫、短答等真实音频测试，看看“文字判断＋静音等待”是否够用；效果不足再拿证据讨论，不能仅因文字分类正确就说不抢话。

### 9．成功后再采集是否清空

:codex-annotation{index="9"}

按本轮明确要求：**上一轮成功收集后，下次真正启动新一轮采集时清空旧值；同一轮超时提醒不清空。** 不把每次ASR分包、停顿或关键词重复出现当作新采集。

测试用“同一轮补念仍累加”与“成功后开启下一轮从0开始”两个相反场景约束。成功需要有可追溯状态；仅临时Partial达到目标位数不自动冒充成功。新一轮启动在系统中须有明确事件，不能只靠关键词一直存在而反复清空。

### 10．是不是担心Partial没有起止时间

:codex-annotation{index="10"}

是，准确说有三项要实测：厂商这条Partial有没有目标片段时间；SDK是否保留；经过适配器后TD是否拿得到。只有整句话的时间但定位不到编号部分，也不能拿来算编号WPM。

这由我做真实调用验证，不再作为产品选择。调用范围提案在下方；未执行前不声称通过。除了字段存在，还会记录多少有效编号片段可可靠计算速度，避免“偶尔有一条带时间”被误报为全面支持。

### 11．回声消除要不要新增模块

:codex-annotation{index="11"}

优先检查和验证浏览器已有回声消除，**不先新增服务端模块**。浏览器已有成熟的`echoCancellation`能力，可读取音轨实际设置；支持/开启不等于当前设备双讲效果已合格。

WebSocket和WebRTC都应检查它们各自真实的麦克风采集链路。先做“只有机器人外放”和“人机同时说”实机测试，确认不把机器人数字再次收集；不通过再定位采集配置、播放参考或硬件原因。纯音频文件混合测试不能证明浏览器AEC有效。

依据：[W3C媒体采集规范](https://www.w3.org/TR/mediacapture-streams/#dom-mediatrackconstraintset-echocancellation)、[浏览器回声消除说明](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)、[实际音轨设置](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings)。未在本轮进行实机AEC测试，未因源码未显式配置就断言依赖没有默认开启。

### 12．是否改成只用Final

:codex-annotation{index="12"}

不是。继续遵守“短等Final，到期用最新Partial”。我的建议是改统计：记录真正提交的是Partial还是Final、何时提交，Final后来到达另记。不能为了适应旧报表，把Partial伪装成Final，也不能为等Final无限拖延。

测试会专门构造“先请求LLM，后收到Final”，确认不会漏轮次、重复回复或产生负延迟。一次用户提交后的工具调用及回答不算第二次用户提交。

## SDD：规格先行

1. 既有Delta Spec和决策记录为起点；本计划不是第二套行为真源，也不意味着核心开发已获批准。
2. 本轮明确的“成功后新采集清空”“纯编号本地、混合表达工具分流”“one moment反例”同步到当前规格。仍需用户选择的行为进入open-questions；工程缺陷进入tasks。
3. 每个测试ID映射Spec的Requirement/Scenario；新增可观察行为必须先有规格。未定行为只准备输入与测试边界，不能写一个自选答案再以测试通过宣称正确。
4. User Gate 1仍需规格与同步后的原型确认。纯技术探针/离线测试准备不冒充正式功能开工或原型冻结。

## 真实调用：分开批准，不与范围确认捆绑

### 第一批优先做：Partial时间戳能力探针

- 接收方：Deepgram（Flux英文、Flux多语种、Nova-3）、Speechmatics enhanced、Soniox stt-rt-v5、AssemblyAI universal-3-5-pro，共六模型。
- 数据：准备3段无客户信息的英文逐位念号录音，每段不超过20秒，分别慢速、快速、带前缀/停顿；16kHz、16bit、单声道PCM。上传前给出精确文件清单、文本、时长、SHA-256及每模型发送次数。不会从客户录音库自动抽取。
- 次数：每段每模型1次，最多18条流式会话、总音频不超过6分钟；不自动重试，不额外调用TTS生成素材。
- 目的：逐层检查Partial内容、接收时刻、音频起止时间、时间粒度、片段覆盖和Final变化。保存脱敏事件及适配输出；这一批不能证明多语种、噪声或生产P95质量。
- 费用：建议申请总费用上限人民币10元；执行前按实际模型费率/最小计费核算。若无法确认上限，先不调用；预计将超预算、模型不可用、权限失败或任何凭证异常立即停止，不换模型偷偷扩大范围。
- 当前授权状态：用户要求工程真实验证时间戳；本批精确文件、费率核算及限定调用预算尚未确认，**未执行、未消耗费用**。这是项目逐次授权要求，不是把技术调查退回给产品。

### 后续批次

Jev语义质量、真实TTS和完整会话另列数据/次数/费用申请。先用本地无敏感样本构造场景，不把ASR探针授权扩展成全链路付费测试。测试语料与调参样本分开，冻结最终验收集；按语言、场景分项报告，不用小样本统计冒充可靠P95。

## 通过标准与证据

- 确定性事件测试：上述已冻结行为全部通过；重复提交、旧范围污染、清空后旧任务回写/播放等禁止事件在场景集中为0。不能以一次幸运通过掩盖可重现失败。
- 时序：假时钟验证精确边界；实际机器另测调度偏差、音频排队和网络时间。最长静音约束的是正常静音路径，不对断流伪造正常计时，也不声称硬实时。
- ASR：六模型逐一给出支持、存在适配缺陷、时间证据不足或未验证；时间不足不触发WPM跟读，但不能把长期无法跟读报为功能全通过。
