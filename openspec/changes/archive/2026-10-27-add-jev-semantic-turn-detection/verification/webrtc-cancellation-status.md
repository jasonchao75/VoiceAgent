# D-052：现有音轨取消方案与证据边界

现有WebRTC音轨可以满足“停止旧回答”的实现方向，没有证据要求更换整条下行传输。A的执行批准已撤回，未采用数据通道PCM传音频。

## 原问题与最小改动

原流程为：TTS生成PCM → SDK输出任务 → RawAudioTrack待发队列 → 原Opus/RTP音轨 → 浏览器播放。原SDK打断取消了输出任务，却未移除RawAudioTrack已排队PCM，所以旧声音可能继续发送。

当前实现保留麦克风上行、连接、信令、音轨与编码：Final使旧响应失效 → 取消旧LLM/TTS并拦截迟到输出 → SDK原生打断 → 清除RawAudioTrack尚未发送的旧PCM并结算等待者 → 同一音轨发送新回答。正式移动页面也补上原先遗漏的远端音轨播放绑定与结束释放。

## 已验证与未保证

- r19实际SDK：取消等待Future后旧队列仍存在的红灯；修复后清队列、新PCM仍能在原音轨发送、未知SDK队列结构明确报错。见development-20261022-r19与tests/test_td_webrtc_cancel.py。
- r20正式页面本地网络：假麦克风与替身厂商，真实WebRTC连接/Opus/RTP；440Hz旧答被截短，随后收到880Hz新答，观察窗口内旧答未回来；桌面与窄屏Chromium通过。见development-20261022-r20/rtc-final-tokenizer.txt及对应诊断JSON。
- r25完整后端591项通过包含上述SDK取消测试；没有重新执行r20浏览器实验。

清除服务端待发音频无法撤回已经进入网络或浏览器抖动缓冲的数据。现有证据不保证任意网络下零尾音，也不提供每段任务的实际硬件停止时刻。真实手机、蓝牙、弱网、真实厂商取消、RTC编号缓存串行组合及精确任务回执仍未验证/未闭环，继续列入交付状态，不能标记完整播放仲裁通过。

下一步沿用原音轨补齐上述组合与证据；若后续确有无法满足已确认契约的架构取舍，再凭具体实验提出方案，不恢复原A/B的未经证实前提。
