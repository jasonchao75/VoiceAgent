## Confirmed finding

**P2 — Disabling number completeness does not disable its settings.** `frontend/src/td-settings.js:91-94` only disables the entire priority-rule fieldset; it never disables `number-length`, `collection-timeout`, `collection-message`, or `overflow-message` when `collection-enabled` is false. `bot-config/spec.md` requires both reminder inputs to be disabled while completeness is disabled. The frozen prototype implements all four fields at `prototypes/index.html:621`.

Reproduced with local Chromium, the formal `/` route and production `main.js`/`td-settings.js` components, with every API intercepted using the existing catalog/Bot fixture. Use a self-developed Bot, priority rule enabled, collection=null; open Advanced → Turn Detection → Priority rules. The completeness switch is off but all four controls report disabled=false. They invite editing although collect() serializes collection=null and ignores those edits. This is a UI/contract mismatch, not a backend failure. The native validation concern was disproved: the form has novalidate and Save succeeds.

Observed result:
```json
{"collectionEnabled":false,"collectionFields":[{"id":"number-length","disabled":false},{"id":"collection-timeout","disabled":false},{"id":"collection-message","disabled":false},{"id":"overflow-message","disabled":false}],"saves":1,"saveState":"Saved"}
```

Fix recommendation: apply completeness enablement on load and on change, matching the frozen prototype. Add a production-page regression that verifies disabled state, re-enable behavior, and saved collection=null. No source fix made during review.
