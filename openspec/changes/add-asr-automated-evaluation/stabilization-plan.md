# ASR Evaluation 稳定性收口计划

## 0. 状态

- Baseline status: Confirmed for gap analysis and phased stabilization planning.
- Confirmed by: Product owner.
- Date: 2026-09-23.
- Source: 当前 Codex 任务；确认原话：“我觉得你写的没问题啊。”随后明确要求：“那你继续？我看看你咋做。”
- Boundary: 本确认授权继续审查和规划，不授权生产数据修改、付费外部调用、E65A 重试或生产发布。

## 1. 目的与结论

本计划用于停止“按线上故障逐点修补”的交付方式，把 ASR Evaluation 收口为可重复、可恢复、可审计的稳定批处理系统。

稳定性收口不等于把现有 Known Issues 逐条关闭。它要求先冻结产品流程，再建立跨模块不变量，随后统一外部调用执行与恢复机制，最后通过分级真实批次证明系统行为。任何单项修复只有同时满足对应不变量和验证门槛，才算进入稳定基线。

本计划当前是候选基线，不替代已确认的 Delta Spec、产品决定或 UI baseline。产品负责人确认后，才将其拆入正式 Spec、design、tasks、测试和发布门禁。

## 2. 收口期间的范围控制

### 2.1 暂停事项

- 暂停新增 ASR Evaluation 产品能力、供应商、指标和页面区域。
- 暂停对 82 通或更大数据集进行完整付费重跑。
- 暂停用生产故障直接驱动临时状态分支、专用重试入口或批次特判。
- 暂停把本地 Mock、单次供应商成功或健康检查当作端到端稳定证据。

### 2.2 允许事项

- 修复会破坏数据正确性、状态真实性、费用边界、幂等性和恢复能力的问题。
- 补充不改变产品行为的可观测性、确定性测试、故障注入和审计证据。
- 在逐次授权、明确数据范围、费用上限和停止条件后执行分级 canary。
- 保留现有生产历史和审计记录；不得为方便测试静默改写历史结果。

### 2.3 本轮不并入的工作

- `add-asr-benchmark-comparison` 的运行协议、排名展示和历史上下文范围决策。
- 新 ASR 厂商横向评测、自动供应商选型和生产 ASR 自动调参。
- 独立队列服务、分布式调度或数据库替换，除非 SQLite 在本计划的并发与恢复门槛下被证明确实不满足要求。

## 3. 四层稳定性基线

## 第一层：冻结产品流程和数据职责

### 目标

让每一种输入、每一个阶段和每一种结果只有一个明确职责，后续工程实现不得重新解释。

### 候选流程

1. **数据校验**：验证并冻结本批次的数据集版本和配置快照。
2. **Pass 1**：只根据完整历史对话筛选疑点事件和额外 Good 候选池，不生成 Ground Truth。
3. **Multi-ASR**：每个命中 conversation 向每家启用厂商提交一次完整 `record`，得到带说话人和时间轴的完整转写。
4. **音频与证据对齐**：以 `user_record` 的语音岛冻结 Case 音频边界；先确定性映射，只有歧义 Case 才调用受控辅助 LLM。
5. **Pass 2**：综合线上历史转写、完整对话和已投影的 provider turn 文本，判断 Good、Bad 或人工复核。
6. **人工复核与报告**：复核不确定 ASR Case 和历史 Turn 异常；冻结报告并将合格样本写入 Benchmark。

### 数据职责不变量

- `conversation_history`：保存被评估的线上历史转写和业务上下文，不提供可信音频边界。
- `record`：每个命中 conversation/provider 最多进行一次完整录音 ASR，提供说话人、真实时间轴和候选文本。
- `user_record`：提供 Case 音频边界、试听和 Benchmark WAV，不再次提交评测 ASR。
- 历史 `time (s)`：仅作审计字段，不参与强制定位、裁片或失败判定。
- 评测 ASR：只提供证据，不被当作 Ground Truth，也不直接产生生产供应商选型结论。
- 辅助 LLM：只能选择真实存在的 event/island/turn ID，不能生成新 ID、时间戳或移动音频边界。

### 建议冻结的产品规则

1. 批次永久绑定创建时的数据集版本；后续上传不得改变历史批次的数据来源。
2. 部分资源失败时，合格 Case 继续执行；未完成 Case 不得进入正式结论或 Benchmark。
3. 负责人可以二次确认“使用现有结果结束”，生成明确标注覆盖范围的 `completed_partial`。
4. 重试前必须显示：将重试的资源、不会重试的资源、预计新增费用和停止条件。
5. 页面严格区分三种统计范围：当前批次、最近冻结报告、跨批次去重累计；不得在同一指标组内混用。

### 第一层退出条件

- 产品负责人一次性确认上述流程、数据职责和五条规则，或逐项给出替代决定。
- Delta Spec、设计、原型和页面术语保持一致，不再同时存在相互冲突的旧流程描述。
- 新需求进入独立 Change，不再插入本轮稳定性范围。

## 第二层：建立数据与状态不变量

### 目标

无论超时、重试、拆组、重启或版本升级，系统都能回答：这批数据是什么、当前有效工作集是什么、哪些结果有效、为什么处于当前状态。

### 必须建立的不变量

1. **数据集不变**：`batch.dataset_id` 与输入清单、文件哈希、Conversation/Event 集合一起冻结；所有查看、恢复、重试和报告都从该快照读取。
2. **配置不变**：Prompt、上下文、词典、模型、协议、价格和预算版本在批次内不可漂移。
3. **工作单位明确**：Pass 1 按 conversation、Multi-ASR 按 conversation/provider、对齐与 Pass 2 按 canonical Case、复核按 Case 或 Turn 异常组计数。
4. **成功单调**：已经持久化且契约有效的成功结果不得因 sibling 失败、页面刷新、重试或重启退回 pending/failed。
5. **当前结果唯一**：批次终态只根据当前 canonical 工作集及其最新有效检查点计算；superseded 父组和历史失败仅用于审计。
6. **尝试记录追加**：每次外部调用、拆组、超时和替代关系追加记录，不覆盖历史；当前结果通过显式 canonical 指针解析。
7. **统计可对账**：页面分子、分母、排除数、任务总数和费用都能追溯到唯一查询范围与稳定 ID 集合。
8. **Benchmark 全局唯一**：以 `(conversation_id, event_id)` 作为已确认全局唯一边界；合并 Case 必须保留所有 source event ID 并逐一参与冲突检查。
9. **费用不消失**：请求发送后即使客户端超时，也不得直接释放为“未花费”；先进入 `usage_unknown` 或等价待核销状态，直到供应商结果或人工对账明确。

### 第二层退出条件

- 用数据库约束或状态投影测试证明上述九条不变量，而不是只靠页面逻辑。
- 任意历史失败组存在时，只要当前 canonical Case 全部成功，批次仍可正确进入下一阶段。
- 同一批次在重启前后得到一致的数据集、工作集、统计与当前状态。
- 当前已知的数据集未冻结、统计范围混用、历史失败污染终态和超时费用漏记问题均关闭。

## 第三层：统一执行、重试与恢复

### 目标

Pass 1、辅助对齐 LLM、Pass 2 和三家 ASR 使用同一套执行语义，不再为每个阶段分别补超时、拆组和幂等逻辑。

### 统一执行器必须负责

1. 在发送前构造最终请求，按供应商真实限制完成输入、Thinking、输出和纠错提示空间预检。
2. 在持久化预算预留和 attempt ID 后才发送外部请求。
3. 使用统一失败分类：发送前确定性失败、可重试传输失败、超时结果未知、结构失败、不可重试供应商失败、预算拒绝。
4. 只调度 `retryable=true` 且仍属于当前 canonical 工作集的资源。
5. 超时或结构失败时按阶段最小业务单元稳定拆组；父组标记 superseded，不原样无限重放。
6. 以“批次 + 阶段 + 输入快照 + 精确成员集合 + attempt”形成稳定幂等身份，防止重复点击、重启或 webhook 产生重复调用和重复计费。
7. 成功业务单元立即事务持久化；一个 sibling 失败不得回滚整组已验证结果。
8. 使用 lease、心跳和过期恢复区分“仍在执行、结果未知、可以安全重试”，应用重启不得自动重复付费调用。
9. 对 SQLite 写入实行有界并发、批量事务和 busy timeout；数据库锁不得被包装成供应商失败。
10. 重试计划为空时不得把批次切回 running，也不得创建预算预留。

### 第三层故障矩阵

每个外部阶段至少覆盖：

- 首次成功；
- 发送前超限；
- 超时但供应商可能已处理；
- 非法 JSON/Schema；
- 不存在或越权 ID；
- 明确不可重试失败；
- 父组拆分后部分成功；
- 成功持久化前/后进程重启；
- 重复点击重试；
- webhook 重复或乱序；
- 预算达到上限；
- SQLite 短暂锁竞争。

### 第三层退出条件

- Pass 1、辅助对齐、Pass 2 不再各自维护互相矛盾的核心重试规则。
- 故障矩阵在确定性测试和本地真实进程恢复测试中全部通过。
- 同一失败操作重复触发不会增加业务结果数，也不会重复派发不可重试任务。
- 费用台账满足“每次已发送调用都有 reservation、settled 或 usage_unknown 记录”。

## 第四层：分级验证和放量

### 目标

明确什么证据可以证明什么，避免“单元测试通过”直接跳到“大批量生产稳定”。

### 验证阶梯

#### Gate S0：静态与确定性验证

- Spec、状态图、数据约束和错误分类一致。
- 单元、属性、迁移、状态投影和故障矩阵测试通过。
- 不调用真实供应商。

#### Gate S1：本地进程恢复验证

- 使用固定 fixture 和可控 fake provider 跑完整六阶段。
- 在每个外部阶段的发送前、等待中、成功落库后强制重启。
- 验证无重复调用、无成功回退、无统计漂移、无费用记录丢失。

#### Gate S2：3–5 通 external-real canary

- 使用固定、小规模、已授权的数据集和费用上限。
- 覆盖一次正常完成，以及一次受控超时/失败恢复场景。
- 所有任务、Case、请求组、费用和报告逐项人工对账。

#### Gate S3：20 通重复运行

- 同一冻结数据集至少运行两次，允许模型结论不同，但输入集合、任务数量、状态流转、幂等和费用账必须可解释。
- 不得出现新的 P0/P1 数据正确性、重复调用、状态卡死或费用失真问题。

#### Gate S4：82 通正式放量

- 仅在 S0–S3 全部通过后，由产品负责人主动创建或明确授权恢复。
- 首次 82 通运行设置费用硬上限和人工观察点，不使用无人值守无限重试。

### 证据等级

- `static`：代码、Spec、Schema 审查。
- `fixture/mock`：确定性输入和模拟供应商。
- `local-real`：真实进程、SQLite、重启和 UI/API，但不调用外部供应商。
- `external-real canary`：小范围真实供应商调用。
- `production batch`：真实完整批次。

低等级证据不能替代高等级证据。每个 Gate 必须保存输入快照、执行版本、检查结果、已知问题和未验证项。

## 4. 实施阶段与交付物

### Phase 0：冻结与清账

- 确认本计划第一层的五条产品规则。
- 把现有 Known Issues 映射到四层，不再按发现顺序排期。
- 冻结稳定性期间允许修改的文件、功能和生产操作边界。
- 交付物：确认后的稳定性基线、问题映射表、风险分级和回滚点。

### Phase 1：数据与状态模型

- 增加不可变 dataset identity 和批次绑定。
- 定义 canonical 工作集、attempt/superseded 关系和状态投影。
- 统一当前批次、最近报告和跨批次累计统计查询。
- 补齐超时调用的 `usage_unknown` 费用状态。
- 交付物：Schema/迁移、状态图、数据不变量测试和兼容性说明。

### Phase 2：统一执行与恢复

- 抽取公共执行器、失败分类、重试计划、拆组和幂等机制。
- Pass 1、辅助对齐、Pass 2 和 ASR 逐步接入；每迁移一个阶段都保留回归门禁。
- 交付物：统一执行契约、故障矩阵、恢复测试和费用对账测试。

### Phase 3：产品状态与操作收口

- 重试前展示计划、费用上限和不可重试项。
- 页面按明确范围展示统计，批次状态与服务端 canonical 投影一致。
- 部分结果、部分完成和最终报告使用清晰且不可混淆的语义。
- 交付物：正式页面更新、双视口状态矩阵、API/UI 对账测试。

### Phase 4：分级 canary 与放量

- 依次执行 S0、S1、S2、S3、S4；不得跳级。
- 每级发现 P0/P1 问题后回退到对应层修复，并重新通过受影响 Gate。
- 交付物：逐级验证记录、费用记录、问题闭环和最终放量建议。

## 5. 优先级和阻塞关系

### P0：先解决，否则禁止真实批次重试

- 历史批次未冻结 dataset identity。
- 超时请求释放预算且没有任何可能已计费记录。
- 重试不识别 retryability，可能重复不可重试或确定性失败。
- 历史失败行污染当前 canonical 终态。
- 成功结果可能因重试或 sibling 失败回退。

### P1：S2 canary 前解决

- 页面统计范围混用。
- 阶段之间重试、拆组和幂等语义不一致。
- 重启、lease 过期和结果未知缺少统一恢复策略。
- 外部任务数、Case 数、请求组数和尝试数不能稳定对账。

### P2：S4 放量前解决或明确排除

- 仓库级既有 Ruff 告警、依赖弃用告警和 GitHub Action Node 运行时告警。
- 尚未覆盖的 Azure/OpenRouter/Qwen 自定义端点 external-real 组合。
- 不影响本次主链稳定性的文案、辅助展示和非核心管理能力。

## 6. 产品负责人需要确认的候选基线

建议将以下五项作为一个整体确认；任一项需要调整时单独指出即可：

1. **流程**：采用本计划的固定六阶段，不再增加或合并阶段。
2. **部分失败**：合格 Case 继续，未完成 Case 排除；负责人可二次确认生成部分覆盖最终报告。
3. **重试控制**：重试前展示范围、不可重试项、预计新增费用和停止条件；无可重试资源时不启动。
4. **统计范围**：当前批次、最近冻结报告、跨批次去重累计分开展示，禁止拼成一组指标。
5. **数据集版本**：每个批次永久绑定创建时的数据集；历史批次不得读取当前活动数据包。

推荐全部采用。确认只冻结产品行为，不等于授权修改生产数据、执行付费调用、恢复 E65A 或发布上线。

## 7. 完成定义

只有同时满足以下条件，才能宣布 ASR Evaluation 稳定性收口完成：

- 四层退出条件全部满足，P0/P1 问题关闭。
- S0–S3 证据齐全，独立验收为 PASS。
- 没有未披露的 Open known issue 或 unverified item。
- 产品负责人完成最终验收并明确授权 S4 或生产发布。
- 回滚路径、生产数据兼容性、费用上限和剩余 P2 风险已书面披露。
